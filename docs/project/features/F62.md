# F62. Worker

**Statut : Vérifiée.** Spec : `asac-specs-v1.md`, § 6, lot C.

## Critères

| # | Critère | Preuve |
|---|---|---|
| 1 | `asac apply -p <p> --enqueue` met un job `run` en file (SQLite dans `.asac-state/`) avec pipeline, run et harness, et rend le numéro | `test_enqueue_puts_a_run_job_in_the_queue_and_returns_its_number`, `test_enqueue_without_a_run_id_names_the_run_for_you`, `test_enqueue_refuses_an_unknown_pipeline_before_queueing` |
| 2 | `asac worker` prend les jobs dans l'ordre, un à la fois, crée le run, l'exécute, marque le job terminé quand le moteur rend un résultat stable (terminé, gate, bloqué) | `test_the_worker_takes_the_job_creates_the_run_and_runs_it`, `test_a_run_that_stops_at_a_gate_is_a_finished_job`, `test_a_blocked_run_is_a_finished_job`, `test_jobs_are_taken_in_order_one_at_a_time` |
| 3 | Un résultat d'erreur marque le job en échec avec sa raison et le replace dans la file, jusqu'à 5 tentatives | `test_an_engine_error_fails_the_job_with_its_reason_and_queues_it_again`, `test_a_job_that_keeps_failing_ends_failed_after_five_attempts` |

| 5 | `asac worker --once` traite les jobs présents et s'arrête | `test_once_handles_every_due_job_then_stops` (borné par un délai : un worker qui ne s'arrête pas fait échouer le test) |
| 6 | Une ligne par job : numéro, run, résultat | `job 1  w1  waiting for gate gate_w1_requirements` |
| 7 | Même runner et même harnais que `asac apply` | `test_the_worker_uses_the_configured_runner_and_harness_like_apply`, `test_the_state_of_a_run_taken_by_a_worker_matches_one_started_by_apply` (même audit) |
| 8 | `asac worker` rejoint le § 10 et `asac --help` | `test_worker_is_in_the_help_and_the_supported_list` |

Avec le vrai Docker : `test_a_worker_runs_a_delegated_run_in_the_real_container` — un job en file,
un worker, un vrai conteneur, le travail dans le worktree, le run arrêté à sa gate.

## Changements

- `src/asac/engine/worker.py` : `work_once` (prend un job, lance le moteur, termine ou replace).
- `asac apply --enqueue`, `asac worker [--once] [--poll]` dans la CLI.
- Le port `JobQueue.claim` reçoit un filtre `kind` optionnel (défaut inchangé), implémenté dans les
  deux adaptateurs. Sans lui, un worker qui prend un job d'un autre type (webhook, reprise) devait
  le « rendre » en trichant sur son compteur de tentatives. Le comportement existant ne change pas ;
  les tests de conformité existants passent, et deux nouveaux couvrent le filtre.
- Un job livré deux fois (livraison au moins une fois) reprend le run existant au lieu d'échouer.

## Vérification

8 mutations, toutes détectées : une erreur du moteur jugée terminée, un blocage rejoué, un plafond
de 50 tentatives, la raison non conservée, tous les types de jobs pris, run recréé au lieu de
repris, `--once` qui ne s'arrête pas (détectée seulement après avoir borné le test par un délai),
filtre ignoré dans l'adaptateur.

## Limites

Le worker est séquentiel : une file, un worker, pas de concurrence entre workers (lot 5 du scope).
La file est SQLite, dans le dossier d'état du projet ; l'adaptateur Postgres respecte le même port.
