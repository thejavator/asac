ASAC — Agentic SDLC as Code

Declare your software delivery. Let agents execute it. v0.2 introduced the 3-layer separation and capability/skill; v0.3 defined the harness as the runtime. v0.4 adds agent governance: knowledge, instructions, budgets, hooks, autonomy level, and the evidence types specific to agentic risks.

Language architecture

Three layers, three concerns

Each layer has a different audience, a different rate of change, and a different gitflow. Mixing them in a single file is a design mistake.

Layer 1
SDLC Manifest
asac.yaml
Audience: tech lead, architect, PO
Declares the WHAT — capabilities, agents, pipelines, evidence types, gates. No concrete values. Portable across all teams in the organization without modification.
Rule: if you see a secret, a concrete URL or Rego code → you are in the wrong layer.
Layer 2
Runtime Config
asac.vars.yaml
Audience: ops, SRE, CI/CD pipeline
Resolves the variables — system URLs, secret refs (Vault, env vars), state backend, concrete harness choices. One file per environment (dev/staging/prod). Often gitignored or encrypted.
Rule: contains only values, never logical structure.
Layer 3
Policies
.asac/policies/*.rego
Audience: security, governance, compliance
Encodes the OPA rules — what agents may or may not do. Independently testable. Can be centralized in a governance repo and referenced from the manifest.
Rule: each .rego file is testable in isolation with opa test.
Analogy: Terraform does the same thing — main.tf (declaration) + terraform.tfvars (values) + Sentinel rules (policies). ASAC applies this pattern to the SDLC.
Resource Types

The 9 core primitives

Each resource belongs to a layer. Layer 1 resources never contain concrete values. v0.4 adds 4 more (section v0.4).

capability

Capability — the WHAT

Logical SDLC type — what a step must accomplish. Vendor-agnostic, reusable across projects. Declares inputs, outputs, and expected evidence.

Layer 1 — Manifest
evidenceType

EvidenceType — the proof

Named proof that a step was completed correctly. spec_reviewed, tests_green, sast_clean — first-class citizens of the language. The set of types is extensible: a registry module (e.g. a Golden Path) can declare its own evidenceTypes, along with the skill that produces them.

Layer 1 — Manifest
skill

Skill — the HOW

Versioned module from the registry that implements a capability in a specific technology context. An agent brings a skill to fulfil a capability.

Layer 1 — Manifest (ref) + registry
provider

Provider

Integration with an external system. Declared with var.xxx for configuration — concrete values come from layer 2.

Layer 1 (structure) + 2 (values)
agent

Agent

AI actor — combines skill + LLM provider + harness + tools. The harness is referenced via var.xxx, not hardcoded.

Layer 1 (structure) + 2 (concrete harness)
pipeline

Pipeline

Ordered SDLC flow — trigger, steps with dependsOn, requiresEvidence, producesEvidence, and gates.

Layer 1 — Manifest
gate

Gate — simplified

Minimal control point: type (human / quality / automated) + role or policy. Complex logic → separate Rego file.

Layer 1 — Manifest (core) + 3 (rules)
variable

Variable

Interface between layers 1 and 2. The manifest declares the expected variables (var.gitlab_url), layer 2 resolves them.

Layer 1 (declaration) + 2 (value)
harness

Harness — extension point

Extensible type, not a fixed enum. The standard defines the interface (what a harness must implement). Concrete values (copilot, claude-code…) are extensions.

Interface in the standard — values in extensions

Relationship capability → skill → agent

capability declares WHAT must be done (e.g. specification_engineering).
skill implements the capability in a technology context (e.g. registry.asac.dev/core/specification@2.1).
agent combines skill + harness to execute at runtime.

You change LLM provider or harness → you only modify the agent or layer 2.
You change the SDLC process → you modify the pipeline and its capabilities.
The two evolve independently.
Complete example

The 3 files of an ASAC project

A single payments-service project — minimal manifest + runtime vars + separate policy.

Layer 1  asac.yaml — SDLC Manifest (versioned, shareable, readable by everyone)

asac.yamlyaml

  workspace: payments-service
  team:      payments

## ── EXPECTED VARIABLES (interface to layer 2) ──────────
variables:
  gitlab_url:   type: string   description: GitLab instance URL
  gitlab_token: type: string   sensitive: true
  jira_url:     type: string
  jira_token:   type: string   sensitive: true
  llm_model:    type: string   default: claude-opus-5-5
  llm_api_key:  type: string   sensitive: true
  ba_harness:   type: harness  description: Harness for BA agent
  dev_harness:  type: harness
  qa_harness:   type: harness

## ── PROVIDERS (structure only, values in layer 2) ──────
providers:
  gitlab:
    source:  asac/gitlab
    version: "~> 2.0"
    config:
      url:   var.gitlab_url
      token: var.gitlab_token

  jira:

  llm:

    version: "~> 1.0"

      model:   var.llm_model
      api_key: var.llm_api_key

## ── CAPABILITIES (the WHAT — vendor-agnostic) ──────────────────
capabilities:
  specification_engineering:
    description: Transform business intent into executable spec
    inputs:  [business_intent, requirement_ticket]
    outputs: [structured_spec, acceptance_criteria]
    evidence: [spec_reviewed]

  implementation:
    description: Produce working code from specification
    inputs:  [structured_spec]
    outputs: [git_branch, merge_request]

  verification:

    inputs:  [merge_request, structured_spec]
    outputs: [quality_report]
    evidence: [coverage_passed, sast_clean, qa_approved]

  release:
    description: Deploy verified implementation to target environment
    inputs:  [merge_request]
    evidence: [deployed]

## ── EVIDENCE TYPES (named SDLC proofs) ─────────────────────
evidenceTypes:
  spec_reviewed:
    description: Spec reviewed and approved by product owner
  tests_green:
    description: All required tests passing
  mr_created:
    description: Merge request created with description
  coverage_passed:
    description: Coverage meets configured minimum threshold
  sast_clean:
    description: No high-severity SAST findings
  qa_approved:
    description: QA engineer manual sign-off
  deployed:
    description: Successfully deployed to target environment

## ── SKILLS (the HOW — versioned modules from the registry) 
skills:
  spec:
    ref: registry.asac.dev/core/specification@2.1.0
    fulfils: specification_engineering  # explicit capability → skill link

  java-impl:
    ref: registry.asac.dev/java/implementation@3.0.0
    fulfils: implementation
    params:
      build_tool:    maven
      test_framework: junit5

  qa:
    ref: registry.asac.dev/core/quality-assurance@2.5.0
    fulfils: verification
    params:
      coverage_min: 85

  release:
    ref: registry.asac.dev/core/release@1.8.0
    fulfils: release

## ── AGENTS (skill + provider + harness via var) ───────────────
agents:
  ba:
    skill:    spec
    provider: llm
    harness:  var.ba_harness          # resolved in layer 2
    tools:    [jira, gitlab]

  dev:
    skill:    java-impl
    provider: llm
    harness:  var.dev_harness
    tools:    [gitlab]

  qa-agent:
    skill:    qa
    provider: llm
    harness:  var.qa_harness
    tools:    [gitlab]

  devops:
    skill:    release
    provider: llm
    harness:  var.dev_harness
    tools:    [gitlab]

## ── PIPELINE ──────────────────────────────────────────────────
pipelines:
  feature:
    description: Full feature lifecycle — Jira story to staging
    timeout: 72h
    trigger:
      type:     event
      provider: jira
      event:    issue_created
      filter:
        issuetype: Story
        labels:    [asac-enabled]

    steps:
      requirements:
        capability:       specification_engineering
        agent:            ba
        mode:             assist              # mode on the step, not on the agent
        requiresEvidence: []
        producesEvidence: [spec_reviewed]
        gate:
          type:    human
          role:    product_owner
          timeout: 24h

      development:
        capability:       implementation
        agent:            dev
        mode:             delegate
        dependsOn:        [requirements]
        requiresEvidence: [spec_reviewed]
        producesEvidence: [tests_green, mr_created]

      verification:
        capability:       verification
        agent:            qa-agent
        mode:             assist
        dependsOn:        [development]
        requiresEvidence: [tests_green, mr_created]
        producesEvidence: [coverage_passed, sast_clean, qa_approved]
        gate:
          type:   quality
          policy: .asac/policies/qa-gate.rego   # complex logic → separate Rego

      release:
        capability:       release
        agent:            devops
        mode:             delegate
        dependsOn:        [verification]
        requiresEvidence: [coverage_passed, sast_clean, qa_approved]
        producesEvidence: [deployed]
        gate:
          type:    human
          role:    product_owner
          timeout: 48h

Layer 3  .asac/policies/qa-gate.rego — Gate logic (testable in isolation)

.asac/policies/qa-gate.regorego
package asac.gates.qa

import rego.v1

# Block when findings exist and no human approved them.
block contains reason if {
	input.findings_count > 0
	not input.human_approved
	reason := "Findings detected: QA engineer approval required"
}

# Block when coverage is below the configured minimum.
block contains reason if {
	input.coverage < input.skill_params.coverage_min
	reason := sprintf("Coverage %v%% below minimum %v%%", [input.coverage, input.skill_params.coverage_min])
}

# Block when a high-severity SAST finding exists.
block contains reason if {
	input.sast_high_count > 0
	reason := sprintf("%v high-severity SAST findings must be resolved", [input.sast_high_count])
}

# Escalate when the gate has been pending for more than 24 hours.
escalate if input.pending_hours > 24
Benefit of the separation: the security team can modify qa-gate.rego, test it with opa test, and have it reviewed in a separate PR — without ever touching the SDLC manifest. The two evolve at their own pace.
Harness — v0.3

Harness — the agentic runtime

A harness is the runtime that turns an LLM into an executable agent: agentic loop, tool access, context management, permissions, interface. Claude Code, Copilot and Cursor are harnesses. An LLM alone is not one.

Position in an agent's composition

Building blockRoleExampleLayer
capabilityWHAT — what the step must accomplishimplementation1
skillHOW — portable, versioned procedurejava/implementation@3.0.01
providerBRAIN — the LLM modelclaude-opus-5-51 + 2
harnessBODY — runtime that executes the loopclaude-code, copilot, cursor2 (via var.xxx)
toolsHANDS — systems accessible via MCPgitlab, jira, sonar1 + 2
agentComposition of the 5 blocks abovedev1
Skills are not part of the harness. An ASAC skill is portable: it lives in the registry, independent of any runtime. The harness receives it — via an adapter that projects it into its native format. This is what lets a developer use Cursor while the team uses Claude Code, on the same manifest.

Standard interface — asac/harness-interface@2.0

MethodContract
mount(skill)Projects an ASAC skill into the harness's native format (adapter)
run(task, context)Executes a task: spec, memory, step inputs, required evidence
tools(mcp_servers)Connects the declared tools via MCP Gateway
permissions(mode)Maps assist / delegate onto the native approval model
emit(event)Reports logs, costs, artifacts and produced evidence back to ASAC
describe()Declares its runtime capabilities: headless, interactive, mcp, streaming
healthCheck()Checks availability and configuration
BREAKING v0.3: execute(skill, context) is split into mount + run. The skill is mounted once per session, then tasks are executed. getCapabilities() becomes describe() to avoid a collision with the capability resource.

  id:         claude-code
  version:    2.0.0
  implements: asac/harness-interface@2.0

  runtime:
    interactive: true     # developer IDE / terminal
    headless:    true     # claude -p, Agent SDK
    mcp:         true
    streaming:   true

  adapter:
    skill_format: claude-skill
    target:       .claude/skills/{skill}/SKILL.md

  permissions:
    assist:   default      # approval on every action
    delegate: sandboxed    # autonomous, sandbox + OPA policy
Execution model

Where does a step run?

The step's mode determines where it runs. The harness must declare the matching runtime, otherwise asac validate fails.

modeLocationRequired runtimeTriggered by
assistPersona's machine (IDE / terminal)interactive: truePush-to-harness: ASAC notifies, the dev opens the task
delegateASAC Runner (server / CI, isolated container)headless: trueASAC Daemon on event (webhook, approved gate)
asac.yaml — explicit execution (optional)yaml
steps:
  development:
    capability: implementation
    agent:      dev
    mode:       delegate
    execution:
      runner:   var.runner_pool   # k8s, gitlab-runner…
      sandbox:  container
      fallback: assist   # if no runner available
$ asac validateoutput
✓ step requirements  ba   assist   copilot     interactive
✓ step development   dev  delegate claude-code headless
✗ step verification  qa   delegate cursor
  harness 'cursor' does not declare headless: true
  → use mode: assist, or override qa_harness in vars
Rule: an IDE-only harness (Cursor) is only valid for mode: assist. A developer's personal choice can therefore never break the team's delegate step — asac validate detects it before any execution.
Agent governance — v0.4

Four primitives and two step attributes

Derived from the analysis of harness engineering (6 pillars). They do not change the v0.3 definition of the harness: the harness remains the runtime. They describe what is provided to it and the limits within which it acts. The language gains only these 4 primitives and 2 step attributes; CLI commands are not primitives.

knowledge

Knowledge — what the agent knows

Knowledge source with provenance, trust_tier, owner and stale_after. Providers: OKF files, MCP server (graph/vector). Pillar 2.

Layer 1 (structure) + 2 (access)
instruction

Instruction — the rules

Versioned project rules (conventions, "never X", output contracts, escalation rules), projected by the adapter to CLAUDE.md, AGENTS.md or .cursor/rules. Pillar 1.

Layer 1 — Manifest
budget

Budget — the limits

Caps per run and per step: tokens, cost, duration, number of iterations. Exceeding = stop and escalate. Pillar 6.

Layer 1 (caps) + 3 (enforcement)
hook

Hook — the control points

Deterministic check run before/after a tool call or a step (secret scan, dependency verification, eval suite). Pillar 6.

Layer 1 (ref) + 3 (rules)
asac.yaml — v0.4 excerptsyaml
knowledge:
  project-okf:
    provider:    okf
    path:        .asac/knowledge
    stale_after: 90d
    trust_tier:  reviewed

instructions:
  - ref: .asac/instructions/security.md

budgets:
  per_run:  { tokens: 2000000, cost_usd: 15, wall_clock: 2h }
  per_step: { iterations: 5 }

hooks:
  pre_tool:  [secret-scan]
  post_step: [deps-verify, eval-suite]

pipelines:
  feature:
    specLevel: 3      # 1 story · 2 versioned spec · 3 executable spec
asac.yaml — step with autonomyyaml
steps:
  development:
    capability: implementation
    agent:      dev
    mode:       delegate    # WHERE it runs
    autonomy:   review      # HOW MUCH freedom
    escalation:
      outside_scope: human
    producesEvidence: [tests_green, deps_verified]
    policies: [no_regression]
autonomyBehaviorAdoption maturity
readonlyThe agent reads and proposes; no writes, no actions on an external systemL0-L1
reviewThe agent acts within its scope; every output goes through a human gate before taking effectL2-L3
autonomousThe agent acts without a human gate within scope; automatic escalation outside scopeL4, proven capabilities
Autonomy doctrine: the autonomous level is not declared without a written document, validated by security and legal, then translated into .rego.

New evidence types and policies

NameTypeRisk covered
deps_verifiedevidenceNonexistent or hallucinated dependencies (slopsquatting): deterministic check against approved registries
no_regressionpolicySecurity degradation between iterations of the same step: non-decreasing score, otherwise blocked
hills_defined, prfaq_approvedevidencediscovery pipeline: the need is framed before entering delivery
tda_signedevidenceArchitecture review before going to production
outcome_reviewedevidenceOutcome review (pivot or scale): Monitor → Plan feedback loop
Skill supply chain: a skill reference can be pinned by digest (core/quality-assurance@2.5.0#sha256:…) and require a valid signature. A silently modified skill could impose dependencies or behaviors; pinning makes the modification detectable.
