The Problem

AI is in every IDE. Your SDLC isn't ready for it.

Teams adopt AI coding tools one by one — Copilot here, Claude Code there — with no shared conventions, no governance, no way to verify what agents actually did.

Without ASAC

✗ Each developer has their own AI workflow — no consistency
✗ BA and QA don't know an agent touched the code
✗ No audit trail — "the agent wrote it" isn't a compliance answer
✗ Context lost between sessions — agents start over every time
✗ No way to enforce "QA agent ≠ dev agent" or "no push to main"
✗ Switching harnesses (Copilot → Claude) breaks everything

With ASAC

✓ asac.yaml — one source of truth for the team's SDLC
✓ BA and PO approve gates in the portal — no YAML required
✓ Every agent action produces evidence — asac audit tells the full story
✓ Shared memory between sessions — agents resume where they left off
✓ OPA policies enforce separation of concerns at runtime
✓ Change var.dev_harness — pipeline unchanged

Key principle: a step can only start if all requiresEvidence evidences are satisfied. If an evidence is missing or fails, the pipeline stops — no deployment without proof.
Quick Start

From zero to an SDLC pipeline in 3 commands

1. Initialize ASAC in your project

# Automatically detects the stack
$ asac init

✓ Stack detected: Java (Maven)
✓ Generated asac.yaml
✓ Generated asac.vars.yaml.example
✓ Created .asac/policies/

# Fill in the variables
$ cp asac.vars.yaml.example asac.vars.yaml
$ asac vars check

✓ All 9 variables resolved

2. Preview the pipeline (without running it)

$ asac plan --pipeline feature \
           --trigger jira:STORY-1234

Plan: pipeline "feature" for STORY-1234

  Step 1 requirements  → agent: ba  (assist)
  Step 2 development   → agent: dev (delegate)
  Step 3 verification  → agent: qa  (assist)
  Step 4 release       → agent: dev (delegate)

  Gates:  2 human  ·  1 quality
  Cost:   ~38,000 tokens estimated
  Time:   ~4h (excl. human gates)

Apply? [y/N]

3. Run

$ asac apply --pipeline feature \
            --trigger jira:STORY-1234

▶ requirements  running...
  ✓ spec produced
  ⏸ gate: waiting for product_owner
  → alice@example.com notified via portal

...

✓ Pipeline complete
  Evidence: spec_reviewed ✓ · tests_green ✓
            coverage_passed ✓ · sast_clean ✓
            qa_approved ✓ · deployed ✓

asac.yaml generated by asac init

asac.yaml — minimal (java stack)yaml
asac:
  spec: "0.4"
  workspace: my-service

variables:
  gitlab_url:   type: string
  gitlab_token: type: string  sensitive: true
  llm_api_key:  type: string  sensitive: true
  dev_harness:  type: harness

providers:
  gitlab:
    source:  asac/gitlab
    version: "~> 2.0"
    config:
      url:   var.gitlab_url
      token: var.gitlab_token
  llm:
    source:  asac/claude
    version: "~> 1.0"
    config:
      api_key: var.llm_api_key

skills:
  java-impl:
    ref:     registry.asac.dev/java/implementation@3.0
    fulfils: implementation
    params:
      build_tool: maven

agents:
  dev:
    skill:    java-impl
    provider: llm
    harness:  var.dev_harness
    tools:    [gitlab]

# Use a quickstart module for everything else
module "feature-pipeline":
  source:  registry.asac.dev/quickstart/java-microservice
  version: "~> 2.0"
  variables:
    dev_agent: dev
The quickstart/java-microservice module automatically configures the standard capabilities, evidenceTypes, and pipelines. You only write them if you want to customize them.
Existing Projects

ASAC on a project already in production

90% of teams have an existing codebase. ASAC is adopted progressively — one step at a time, without breaking what works.

New project
✓asac init --template java — full pipeline in 5 min
✓Clean evidence chain — everything starts from scratch
✓Maturity L2-L3 possible from the first sprint
✓No existing conventions to respect
Existing project
→asac init --mode observe — analyze first
→Evidence bootstrapped from existing tests
→L1 required at entry, progressive ramp-up
→Legacy and feature pipelines coexist

The 4 adoption phases on an existing project

Phase 1
Observer
Week 1-2
ASAC analyzes the repo — stack, conventions, current coverage. Generates a descriptive asac.yaml . No agent runs.
$ asac init --mode observe

✓ Stack detected: Java / Maven / Spring Boot
✓ CI: GitLab CI
✓ Coverage baseline: 61%  (target: 85%)
✓ Generated asac.yaml (observe mode — no execution)
Phase 2
Assist
Month 1
Enable a single step in mode: assist — the agent proposes, the human validates everything. Start with the least risky capability: spec or code review.
Example: the BA agent generates the user stories, the PO approves them. The dev agent does not touch anything yet.
Phase 3
Bootstrap
Month 2
Produces baseline evidence for the modules you want to cover. Bootstrapped evidences are marked differently — the dashboard distinguishes them from evidences produced by agents.
$ asac evidence bootstrap --scope payments/core

✓ tests_green:     bootstrapped (coverage: 61%)
⚠ sast_clean:      bootstrapped with 3 warnings
  Target 85% coverage tracked as improvement goal
Phase 4
Delegate
Month 3-6
New features move to mode: delegate with automatic gates. Legacy code stays in mode: assist. Both pipelines coexist.
pipelines:
  feature:       # new stories → L3, full gates
    steps:
      development: mode: delegate
  legacy-refactor: # existing code → L1, all in assist
    steps:
      development: mode: assist
  hotfix:        # urgent → minimal, SAST only

Fundamental rule

L0
Human only
Observe mode
→
L1

mode: assist
→

Never delegate before having proven you can assist. Maturity is per capability — a project can be L3 on spec and L1 on deploy.
How It Works

Plan → Apply → Evidence

ASAC follows Terraform's declarative cycle — preview before acting, persisted state, immutable proof.

📝
Declare
Write asac.yaml — what the SDLC must do, not how.
🔍
Plan
Preview agent actions — who does what, estimated cost, human gates.
▶
Apply
Agents execute. Each step blocks on gates and produces its evidences.
🔒
Evidence
Immutable proof in the state. The complete audit trail is available for compliance.

Contributing

Build the standard together

ASAC is designed to be an open standard, not a closed product. The most useful contributions today:

Skills & Modules

Publish skills for your favorite tech stack (Go, Rust, PHP…) or modules for specific SDLC patterns.

Providers

Implement a provider for an uncovered tool — Linear, Azure DevOps, Notion, Bitbucket, ServiceNow…

Harness Extensions

Adapt ASAC to a new AI harness — LangChain, CrewAI, LlamaIndex, AutoGen…

Policy Library

Contribute reusable Rego policies — OWASP compliance, sector-specific rules (finance, healthcare…).

Language Spec

Propose RFCs for new resource types, composition patterns, gate model extensions.

Runtime Engine

Implement the YAML parser, the plan/apply engine, state management — this is the core of the project.

Principle: ASAC must remain an open standard, like HTTP or OpenAPI — not a platform controlled by a single vendor. The spec lives in this repo, the reference implementation is Apache 2.0, and anyone can implement their own compatible runtime.
